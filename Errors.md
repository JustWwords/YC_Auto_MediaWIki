# Инструкция по устранению неисправностей

В данном документе собраны основные критические ошибки, возникающие при развертывании и эксплуатации инфраструктуры, а также инструкции по их устранению.

## Перевод реплики в режим главного сервера

Основной сервер базы данных (по умолчанию `vm_2`) вышел из строя. Кластер репликации сломался, веб-серверы MediaWiki выдают ошибку подключения к БД. Необходимо вручную одну из выживших реплик сделать основным (Master-сервером) и перенаправить на неё остальные.

### Шаг 1. Продвижение реплики до главного сервера (Promote)

Зайдите по SSH на сервер, который вы выбрали в качестве нового Master (например, `vm_3`):

1. Выполните команду продвижения от имени системного пользователя `postgres`:

   ```bash
   sudo su - postgres 
   ```

   ```bash
   pg_ctlcluster 16 main promote
   ```

*(Примечание: замените `16` на вашу текущую версию PostgreSQL, если нужно).*

2. Проверьте статус СУБД. База должна выйти из режима ожидания и начать принимать запросы на запись:

   ```bash
   psql
   ```

   ```bash
   SELECT pg_is_in_recovery();
   ```

*Ожидаемый ответ:* `f` (False). Это означает, что сервер стал полноценным Master.

### Шаг 2. Перенаправление веб-серверов MediaWiki

Пока вы не обновите IP-адрес новой базы данных, веб-ресурсы работать не будут.

1. На Вашей машине обновите файл `inventory.yml` в Ansible, указав новый IP для переменной основного хоста БД (поставить в mainWiki новый основной сервер).
2. Выполните следующую команду, чтобы обновить IP-адреса в `LocalSettings.php`, `zabbix_server.conf` и конфигурационном файле Nginx, а также перенастроить репликационные базы данных:

   ```bash
   ansible-playbook playbook.yml --tags "update, wiki_server_replica_db"
   ```

### Шаг 3. Перевод старого Master-сервера в режим реплики

Если старый Master вернулся в строй, его нельзя просто так включать, его нужно принудительно перевести в режим реплики. Для этого можно повторить 2 шаг, где в `inventory.yml` будут все машины, в том числе и старый мастер, или вручную:

1. Остановите службу PostgreSQL на старом мастере:

   ```bash
   sudo systemctl stop postgresql
   ```

2. Очистите старую директорию данных (замените `16` на вашу версию):

   ```bash
   sudo -u postgres rm -rf /var/lib/postgresql/16/main/*
   ```

3. Сделайте базовый бэкап с **нового** Master-сервера (выполняется на старом мастере):

   ```bash
   sudo -u postgres pg_basebackup -h IP_НОВОГО_MASTER -D /var/lib/postgresql/16/main -U syncuser -P -v -R
   ```

4. Создайте файл-маркер, указывающий PostgreSQL, что он должен запуститься в режиме реплики (recovery):

   ```bash
   sudo -u postgres touch /var/lib/postgresql/16/main/standby.signal
   ```

5. Запустите СУБД:

   ```bash
   sudo systemctl start postgresql
   ```

## Полное восстановление MediaWiki из бекапа

Этот раздел описывает процедуру полного восстановления инфраструктуры и данных с нуля.
Предположения и подготовка:

- Имеются резервные копии баз данных и файлов.
- В `inventory.yml` указаны правильные ip хостов: `vm_1` (proxy) и группа `wiki` (`vm_2`, `vm_3`, `vm_4`).

1. Восстановление виртуальных машин (при отсутствии)
Восстановите виртуальные машины вручную или через Terraform:

```bash
terraform init
terraform apply -var-file=terraform.tfvars
```

2. Запуск Ansible-плейбука для базовой настройки

```bash
ansible-playbook playbook.yml -i inventory.yml
```

Этот шаг должен установить Nginx, PostgreSQL, MediaWiki, Zabbix.

3. Копирование бекапа

Скопируйте соответствующие дампы из хранилища бэкапов(vm_1) на хост с главной СУБД (vm_2).
Следующее выполняется на машине с бекапами (vm_1):

Найдите послелний бекап:

```bash
cd /home/user/backups/postgres/ИМЯ_ХОСТА_БД
ls
```

```bash
ssh -t user@IP_VM_2 "sudo su - postgres -c 'dropdb --if-exists my_wiki && createdb -O wikiuser my_wiki'"
zcat backup_name | ssh -t user@IP_VM_2 "sudo su - postgres -c 'psql -d my_wiki'"
```

4. Восстановление файлов MediaWiki

Скопируйте соответствующие бекапы из хранилища бэкапов(vm_1) на хосты (vm_2, vm_3, vm_4).
Следующее выполняется на машине с бекапами (vm_1):

Найдите послелний бекап:

```bash
cd /home/user/backups/mediawiki/ИМЯ_ХОСТА_БД
ls
```

```bash
ssh user@IP_VM_2 "sudo rm -rf /var/lib/mediawiki/mediawiki-1.46.0/*"
cat backup_name | ssh user@IP_VM_2 "sudo tar -xzf - -C /var/lib/mediawiki/mediawiki-1.46.0"
```
